# Commit

## A convention guessed from the newest subjects

Write the subject in the convention the history uses, and decide which one
that is from enough subjects to tell conventions apart. The newest few can
all share one prefix that fits more than one convention.

`docs:` is the usual trap. Under Conventional Commits `docs` is a type.
Under Scoped Commits every subject is `<scope>: <description>`, where the
scope is the subsystem or module the commit touches, so `docs:` is just
the scope of a documentation change. A log whose newest entries are all
`docs:` fits both.

Read subjects (`git log -20 --format=%s`, or more) until one fits only one
convention: a type such as `feat`, `fix` or `chore` on a code change, or a
parenthesised scope, points to Conventional Commits; a module,
directory, or `treewide` before the colon points to Scoped Commits. In a
scoped history, the subject names the module the change touches, not what
kind of change it is.

## Generated code committed with the change that needed it

Generator output goes in a commit of its own, with nothing hand-written
in it: not the feature that uses the output, and not the source the
generator read (a schema, a `.proto`, a data file). The source goes with
the change it serves. A reviewer can then skim the generated commit as
mechanical output and review the rest on its merits.

A file is generated when it carries a banner such as `Code generated by
... DO NOT EDIT.`, or `.gitattributes` marks it `linguist-generated`. Its
commit's subject is `chore: regenerate code`; a scope is allowed, as in
`chore(pb): regenerate code`.

## Separate changes bundled because their hunks overlap

Changes you can describe separately go in separate commits even when they
meet in one file or on one line. Overlapping hunks make the split more
work, not wrong; "the edits share the same loop" is not a reason to
bundle.

Copy the finished files aside first. Then build each commit's version of
a shared file by hand: start from the committed version (`git show
HEAD:<path>`), apply only that commit's change, stage it, and commit.
Restore the finished files at the end and check that nothing is left
over. Commit a mechanical change (a rename, a move, a reformat) first and
alone, so its diff shows no change in behaviour.
